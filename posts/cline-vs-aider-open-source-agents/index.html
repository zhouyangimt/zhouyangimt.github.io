AI Agent 全解析：Cline + Aider——一个活在编辑器里，一个活在终端里

2026-11-10 AIAgent工具教程编程

同一句话，两种下场

需求就一句：把 requests 换成 httpx，app/ 下面五个文件。

在 Cline 里，它先把五个文件读一遍，然后把改动一条一条摆出来：改 import、改调用、改测试里的 mock、跑 pytest、报错、再改。你在旁边点 approve，一共点了十九次。二十分钟过去，它交付了，你每一行都看过。

在 Aider 里，aider app/*.py，敲同一句话，回车。四十秒后终端回到提示符，git log 多了五个 commit，pytest -q 全绿。

这不是「谁更强」。这是两个工具对同一个问题给出的两种答案：人站在循环的哪个位置。Cline 把每一步都摆到你面前等你签字；Aider 把人挪出循环，改用 git 提交当作「可撤销的签字」。

上一篇（LangGraph 多步骤工作流）结尾说「回到工具侧」。这篇就拆这两个开源代码 Agent，两个都装过、都用废过，坑是真踩出来的。

两个循环长什么样

先把两台机器的骨架并排画出来，后面每一节都对应图里某个位置：

注意两条流程里「人」出现的位置：左边每个方框之间都卡着一次审批，右边人只在最开始说一句话、在最后看一眼。骨架的其余部分几乎一样——都是「上下文 → 模型 → 动作 → 观察 → 再来一轮」。

所以真正的差别只有三处：上下文从哪来、代码怎么落盘、错了怎么回头。 下面一节一个。

上下文：你手边的东西 vs repo map

Cline 的上下文就是你手边的东西：打开的文件、目录树、终端输出、你截的图。你 @ 一下文件它就读，你在终端里报错它能看见。好处是「你正在看的，就是它看的」；坏处是它不知道你没打开的那些文件里发生了什么。

这个活的失败形态特别典型：改完能跑，测试也过，但线上另一个 entrypoint 还在 import requests，因为那个文件你没开、它也没找。等你发现的时候，报错信息指向的是一个它从没读过的模块。

Aider 走另一条路：repo map。用 tree-sitter 把整个仓库解析成符号树（函数、类、方法、调用点），再按引用关系排序，在最相关的位置上花 token 预算，把「地图」塞进提示词，然后才按需读具体文件内容。配置里那个 map-tokens，就是这张地图的预算，不是整个上下文窗口：

# .aider.conf.yml
model: deepseek/deepseek-chat
map-tokens: 2048          # 地图预算，不是上下文窗口
read: [CONVENTIONS.md]    # 只读不写：约定、命名、禁区
auto-commits: true
test-cmd: "pytest -q"
auto-test: true           # 改完自动跑，失败把输出塞回对话

2048 这个数要按仓库大小调。地图给太大，会挤掉真正的文件内容，模型开始「看着地图猜代码」——症状是它引用一个函数名，但那个函数签名它其实没见过。我的经验区间是 1k~3k；再大就该用 --read 明确点名，把预算花在你确定相关的那几个文件上。

编辑协议：整文件重写 vs SEARCH/REPLACE

这是两者最本质的差别，也是 Aider 最值得学的地方。

Cline 的写文件工具就两种：write_to_file 整文件覆盖，replace_in_file 片段替换。整文件覆盖对模型最省心——不用精确匹配任何东西——但一个 600 行的文件改三行，它要吐出六千 token，而且抄错一行的概率随输出长度线性上升。我在一个 800 行的数据处理脚本上见过它把两个几乎同名的变量在中间某段对调了，语法完全合法，跑起来结果错得很安静。

Aider 反过来，强制模型只输出补丁块：

<<<<<<< SEARCH
import requests
=======
import httpx
>>>>>>> REPLACE

配合「SEARCH 段必须在文件里唯一匹配」的规则，输出量小一个数量级，改三行就是改三行。代价是匹配必须精确。我用五十行把这个协议复刻了一遍，专门看它怎么失败：

def parse(text):
    blocks, cur, mode = [], None, None
    for line in text.splitlines():
        s = line.strip()
        if s == "<<<<<<< SEARCH":
            cur, mode = {"search": [], "replace": []}, "search"
        elif s == "=======" and cur is not None:
            mode = "replace"
        elif s == ">>>>>>> REPLACE" and cur is not None:
            blocks.append((cur["search"], cur["replace"])); cur = None
        elif cur is not None:
            cur[mode].append(line)
    return blocks

def apply(src, search, replace, fuzzy):
    find, repl = "\n".join(search), "\n".join(replace)
    if find in src:
        return src.replace(find, repl, 1), "exact"
    if fuzzy:                                  # 只容错行尾空白
        lines = src.splitlines()
        want = [l.rstrip() for l in search]
        for i in range(len(lines) - len(want) + 1):
            if [l.rstrip() for l in lines[i:i + len(want)]] == want:
                return "\n".join(lines[:i] + replace + lines[i + len(want):]), "rstrip"
    return src, "MISS"

源文件是一个用 requests 抓价格的小模块，模型回了一个含四个块的补丁。逐个块跑匹配，终端里是这样：

$ python3 mini_edit.py payload.json
block#1: exact=exact  rstrip=exact
block#2: exact=exact  rstrip=exact
block#3: exact=MISS  rstrip=rstrip
block#4: exact=MISS  rstrip=MISS

四种情况，三种结局：

block#1、#2 精确命中。 正常路径，没什么可说。

block#3 的 SEARCH 段末尾多了一个空格。 精确匹配失败，rstrip 那层容错把它救回来了。这也是真实 Aider 里最常见的「我以为它没改，其实改了」。

block#4 的 SEARCH 段缩进是八格，源文件里是四格。 rstrip 只管行尾，缩进差在行首，两层都救不回来——直接 MISS。

然后是最要命的部分。加上容错重跑一遍，把每个块应用后的文件打出来：

block#1 -> exact
block#2 -> exact
block#3 -> rstrip
block#4 -> MISS
import httpx

def fetch_price(symbol):
    url = f"https://api.example.com/quote/{symbol}"
    r = httpx.get(url, timeout=10)
    r.raise_for_status()
    return r.json()["price"]       # ← block#4 想改成 float(...)，没改成

def fetch_many(symbols):
    return {s: fetch_price(s) for s in symbols if s}

文件能 import、能跑、语法没坏，import httpx 和调用都改对了，只有第 4 处修改不在。这就是 diff 式编辑的静默失败：它不抛异常，不打断流程，命令照样退出 0。

所以 review 这类改动时，别只看「它改了什么」，要数「该改几处、改了几处」。Aider 官方也吃这个亏——它的处理是把 MISS 的块报给模型重试，但模型第二次抄错同样的缩进并不罕见。这也是我给它配 --auto-test 的原因：类型和测试是唯一不撒谎的验收方，返回值从 float 变回字符串这种事，跑一次断言比看十遍 diff 都管用。

反过来说，Cline 的整文件重写没有这个失败模式，但它有另一个：模型顺手「优化」了文件里它没被要求动的二十行。你 diff 里能看出来，但得逐行看。它给你逐条 approve，就是为了让你在这个位置上抓住它。

一个回合的完整往返

Aider 单次交互里最值钱的一步不是生成代码，是 commit。把它摊开成时序：

「一个回合一个 commit」听起来像洁癖，实际上是它整套安全模型的地基：/undo 就是 git reset --hard HEAD~1，「AI 改坏了」从事故降级成一次操作。Cline 也有 checkpoint，但那是 VS Code 内部的影子快照，不进版本历史——换台机器、换个编辑器就没了，也没法 git bisect 出「哪一回合引入的 bug」。

代价是 history 会脏。长任务里我会关掉自动提交（--no-auto-commits），改完自己 git add -p 分组，压成两三个有意义的提交再进 PR。毕竟给同事 review 的是你的提交历史，不是 Aider 的工作日志。

实战：两个场景，两种用法

场景 A：跨文件机械替换，用 Aider。

git status --short          # 必须先干净，否则回滚点不明确
aider app/*.py tests/*.py \
      --model deepseek/deepseek-chat \
      --map-tokens 2048 \
      --test-cmd "pytest -q" --auto-test

进去之后只说一句「把 requests 换成 httpx，同步改测试里的 mock」。观察三件事：每回合的 commit 消息是不是说清了改了什么、pytest 是不是它自己跑的、失败之后它是不是只重发失败的那一块而不是整个文件。第三个最能看出工具成熟度——重发整个文件，等于把 diff 式编辑省下的 token 又还回去了。

场景 B：不熟的代码库、要眼看 UI，用 Cline。

这时候在仓库根目录放一个 .clinerules，把它能自由发挥的空间先压小：

- 禁止 write_to_file 整文件重写，只允许 replace_in_file
- 禁止执行 rm / git reset --hard / docker / 任何 npm publish
- 改完必须跑 `pytest -q`，把原始输出贴出来，不要总结
- API 不确定就先读源码，禁止按记忆写参数名
- 每次改动不超过两个文件，超了先问我

最后一条尤其重要。Cline 真正的敌人是 approve 疲劳：点到第十五次的时候你已经不看 diff 了，手指比脑子快，那时候它和「无人审批」没有任何区别。规则的目的不是限制它，是让前十四次审批都值得看。

怎么选：一句话

要看得见每一行，选 Cline；要一次改一片，选 Aider。

更准确一点，看任务需要人在哪里：

· 需要「人在中途做判断」——不熟的库、要亲眼看 UI、要跑危险命令 → Cline。
· 任务是「人已经想清楚了，只差手」——批量重构、补测试、改 API 调用 → Aider。
· 服务器上没有 IDE、只有 SSH → 只能 Aider。
· 老项目还没有 git → 两个都别用，先 git init。

它们也不冲突。我上周那篇博客的数据迁移就是这么干的：Cline 在编辑器里摸清两个 schema 的差异、写第一版适配层（我需要随时打断它、随时看它读的文件）；路线清楚之后，把剩下 23 个文件的机械改动丢给 Aider 批量铺开。一个负责想清楚，一个负责做完。

三个坑

一、没 git 别碰 Aider。 它的安全感和回滚全建在 commit 上，没有 git 它就是个会直接覆盖你文件的黑盒。新项目第一件事 git init 加一个空 commit，再做别的。

二、repo map 不是越大越好。 我在一个 400 多个 Python 文件的仓库上把 map-tokens 拉到 8000，结果模型开始引用不存在的函数——地图占满了窗口，真正的代码反而进不来。降到 2000 并显式 --read 三个文件，问题立刻消失。上下文塞满的模型，比上下文干净的模型更笨。

三、静默失败要靠测试抓，不能靠眼睛。 就是上面 block#4 那种。我的规矩是：凡是 Aider 的改动，合并前必须看到一次真实的 pytest 输出，如果没有测试就先补一个最笨的断言。看完 diff 就合并，迟早会漏一处——漏的那处通常正好是边界条件。

一句话

这两个工具都没有让模型变强，它们干的是同一件事：把「AI 改代码」这件不可控的事，拆成可审、可撤回、可复现的步骤。 Cline 拆在审批上，Aider 拆在 git 上。你选哪个，其实是在选自己愿意在哪一步花注意力——是十九次点击，还是事后一次 git diff HEAD~5。
